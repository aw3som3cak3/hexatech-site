# ADR-0064: Editorial corrections — ADR-0033, ADR-0040, ADR-0044, ADR-0049

- **Status:** Proposed
- **Date:** 2026-11-09
- **Principles:** P1, P2, P10
- **Amends:** ADR-0033 (PQC cert size claim), ADR-0040 (blood type rationale),
  ADR-0044 (session expiry clock), ADR-0049 (polymer component identification)

## Context

A cross-consistency review of the ADR corpus identified four factual errors in accepted
ADRs. None changes a design decision; all correct inaccurate supporting claims or missing
security notes that could mislead future implementers or procurement reviewers.

Per the ADR process, accepted ADRs are not rewritten. This ADR records each correction
formally and supersedes the specific text it corrects.

---

## Corrections

### Correction 1 — ADR-0033: CVCA cert lives in the reader, not on the chip

**Erroneous text in ADR-0033 (Consequences, lines 88–90):**
> "A hybrid CVCA root cert carrying P-256 + ML-DSA-44 + SLH-DSA-128s keys and all three
> signatures is approximately 12–15 KB. Certificate chain depth directly affects chip B's
> memory budget."

**What is wrong:** In EAC architecture, the CVCA root certificate lives in the reader's
trust store — not on the chip. Additionally, the original text conflates four distinct
credential roles: (1) issuer-signed data provenance (Document Signer / DS certificate,
the issuing authority's credential that signs document data — may be stored on chip for
reader convenience, but belongs to the issuer, not the chip); (2) chip authentication
(the chip's own ECDH/ECDSA key pair, generated on-chip, with an enrollment certificate
issued by the enrollment authority — this is the chip's own credential); (3) terminal
authorization (Card Verifiable / CV certificates — compact binary format, BSI TR-03110,
used by terminals and presented to the chip, not stored on the chip); (4) trusted roots
(CVCA-equivalent trust anchor public key, optionally stored on chip for terminal cert
verification). The 12–15 KB root cert figure is never provisioned onto the chip; it
lives in the reader's trust store.

**Corrected statement:** For Hexa's EAC-style architecture, the chip holds four distinct
credential roles. Each has a separate storage footprint:

1. **Issuer DS certificate** (issuing authority's Document Signer cert, stored on chip so
   readers can verify data signatures): standard X.509, ~1–2 KB classical / ~2–4 KB hybrid PQC.
   This is the *issuer's* credential, not the chip's own authentication credential.

2. **Chip enrollment key pair + certificate** (the chip's own ECDSA key pair generated
   at enrollment; associated certificate issued by the Hexa enrollment authority binding
   the chip public key to the enrollment record): key pair ~32–65 bytes; cert ~1–2 KB.
   This is the chip's own credential for signing treatment records and active authentication.

3. **CVCA-equivalent trust anchor** (public key of the root CA whose chain is used to verify
   terminal CV certificates; stored on chip, not the full cert): ~32 bytes for P-256,
   ~1.3 KB for ML-DSA-44.

4. **Terminal CV certificates** (Card Verifiable certificates per BSI TR-03110 — a compact
   binary format entirely distinct from X.509, without distinguished-name subjects or
   TLV-encoded extensions, ~200–400 bytes classical / ~1.5 KB hybrid) are **not stored on
   the chip**. They are held by terminals and presented to the chip during terminal
   authentication.

The 12–15 KB figure applies to the CVCA root cert in the **reader's trust store**.
The applet specification ADR must size chip storage against roles 1–3 above, not against
the root cert figure, and must specify each role's credential type and footprint separately.

### Correction 2 — ADR-0040: remove unsupported portable-analyser claim

**Erroneous text in ADR-0040 (Alternatives considered — blood type):**
> "portable analysers make pre-engraved blood type unnecessary in any context where the
> NFC tag would be used."

**What is wrong:** This claim is factually incorrect in many conflict and disaster-response
settings. Portable blood-type analysers exist but are not standard kit in mass-casualty
triage, austere environments, or civilian emergency response. ADR-0014's reasoning is
independently sufficient: *wrong blood type causes direct patient harm*. The
portable-analyser clause adds a claim that weakens the argument rather than supporting it.

**Corrected statement:** The portable-analyser sentence is retracted. The rationale for
rejecting blood-type engraving rests on ADR-0014 alone: a blood type that is wrong (due
to transcription error, clerical error, or a tag that becomes stale) causes direct
irreversible patient harm. No pre-engraved field that can be acted on when wrong belongs
on the tag. ADR-0014's reasoning is sufficient; no further claim about analyser
availability is needed.

### Correction 3 — ADR-0044: note session-expiry clock dependency

**Missing text in ADR-0044 (Consequences):**
ADR-0044 acknowledges that "a stolen phone with an active session remains authenticated
until expiry" but does not note that session expiry is enforced by the verifier's local
clock (the phone), which an attacker who controls the phone can advance or freeze to
extend sessions indefinitely. ADR-0004's ratchet clock guards certificate freshness on
the chip — it does not govern session token expiry on the phone.

**Addition to ADR-0044 Consequences:**
Session expiry depends on the verifier's local clock. An attacker with control of the
phone can manipulate that clock. The applet specification ADR for the session-token
function (required by ADR-0057 Decision 3) must not rely on wall-clock APIs
(`System.currentTimeMillis()` or equivalent) for token expiry enforcement.

Two mitigations apply at different layers, and they should not be conflated:

**Reader-app layer (protects the app's signing key):** the reader app should use OS
keystore auth-bound keys to prevent the app's local signing key from being used after a
timeout:
- **Android**: `KeyMint`/`Keymaster` `setUserAuthenticationParameters(timeout, type)`.
  The TEE requires fresh user authentication before the key can be used again.
- **iOS**: Secure Enclave access-control with `.userPresenceRequired` and a reuse duration.
  The Secure Enclave enforces the timeout; application-layer time is not consulted.

These protect the app's credential from being replayed on a stolen phone. They do NOT,
by themselves, expire the JCOP applet's internal session state.

**JCOP applet layer (protects privileged applet operations):** without a trusted on-chip
clock, the applet must not promise absolute elapsed-time session expiry. Instead, the
applet specification ADR must design for:
- **Per-operation fresh challenges**: the applet issues a new challenge for each privileged
  command; the reader must sign the challenge with a fresh user-auth-attested credential.
- **Operation counters**: the applet records the number of privileged operations in a session
  and enforces a session limit.
- **Explicit session invalidation**: the applet provides a session-close command that the
  reader app calls on power cycle, app background, or user sign-out.
- **Explicit residual-risk acceptance**: document that a captured, attacker-controlled
  communication path can replay previously-authorised commands within the session window;
  accept this residual risk or bound it with the counter limit.

The applet specification ADR must state which of these controls it implements and what
residual risk it accepts.

### Correction 4 — ADR-0049: identify the correct polymer element

**Erroneous text in ADR-0049 (Alternatives considered — first alternative):**
> "the tab (polymer in ADR-0048 construction) may not survive fire"

**What is wrong:** ADR-0048's chain-mount tab is part of the Ti Gr5 outer shell. The
polymer element in ADR-0048 is the inner electronics carrier inside the bore — not the
tab. The tab is titanium and would survive fire. The UUID cylinder argument is correct
(the cylinder keeps the UUID on the chain independent of card or carrier survival), but
the supporting claim misidentifies which element is polymer.

**Corrected statement:** "The polymer inner carrier (ADR-0048 Construction B) may not
survive fire. The Ti tab would survive, but attaching the UUID cylinder to the chain
hole keeps the UUID accessible on the chain independent of card or carrier survival —
providing a robust fire-survival fallback regardless of whether the carrier is Ti or
polymer."

## Principle tests

**P1 (break-glass offline; attributable):**
Correction 3 strengthens P1 by replacing wall-clock session expiry with challenge-based,
per-operation authorization at the JCOP applet layer, combined with OS keystore auth-bound
keys at the reader-app layer. This reduces the window for session-replay attacks on stolen
devices. Residual risk (attacker with control of the communication path) must be explicitly
accepted in the applet specification ADR. ✓

**P2 (tag is cache, not identity):**
No change to P2. Corrections 1 and 4 clarify supporting claims without altering the
tag-as-cache model. ✓

**P10 (adopt existing standards):**
Correction 1 aligns the memory budget discussion with actual EAC architecture, with four
distinct credential roles (issuer DS cert, chip enrollment key pair, CVCA trust anchor,
terminal CV certs). Correction 3 names established platform APIs: Android KeyMint
auth-bound keys and iOS Secure Enclave access control for the reader-app layer; ISO 7816
challenge-response sequences for the applet layer. ✓

---

## Consequences

These are editorial corrections. No design decision changes. No re-testing or re-validation
of hardware, protocols, or prior decisions is required.

The applet specification ADR (required before pilot development begins) must incorporate:
- Correction 1: use the per-credential chip-storage figures (DS cert ~1–4 KB; CA key pair
  ~32–65 bytes; optionally CVCA trust anchor key ~32–1,300 bytes), not the 12–15 KB root
  cert figure; also distinguish the four credential roles (issuer signing / DS cert,
  chip authentication / CA key pair, terminal authorization / CV cert at the reader,
  trust anchors)
- Correction 3: require (a) OS keystore auth-bound keys at the reader-app layer, plus
  (b) JCOP applet-layer challenge-based authorization, operation counters, and explicit
  session invalidation — do not rely on elapsed-time expiry without a trusted on-chip clock
