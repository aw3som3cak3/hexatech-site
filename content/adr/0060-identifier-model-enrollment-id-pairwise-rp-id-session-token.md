# ADR-0060: Identifier model — enrollment ID, pairwise RP ID, and session token

- **Status:** Proposed
- **Date:** 2026-11-09
- **Principles:** P2, P5, P7, P9
- **Amends:** ADR-0040 (short-ID derivation), ADR-0057 Decision 2 (refines UUID definition)
- **Resolves tension with:** ADR-0024 (pairwise IDs), ADR-0036 (consumer session ID), ADR-0049 (UUID on reissue)
- **Resolves:** OQ-23 (short-ID as physical correlation vector)

## Context

Three distinct identifier concepts are referenced across multiple ADRs without a single
authoritative definition. The result is an internal contradiction that the reviewer correctly
identified:

- **ADR-0040** derives the engraved short-ID from the chip UUID, making it hardware-bound.
- **ADR-0057 Decision 2** says the UUID identifies the enrollment relationship and is
  independent of chip hardware.
- **ADR-0049** says reissue regenerates the same UUID — which is impossible if it is derived
  from chip hardware.
- **ADR-0024 / ADR-0036** define a per-session random identifier for consumer-mode NFC
  to prevent tracking.
- **OQ-23** notes that the engraved short-ID is a stable physical correlation vector that
  bypasses the software-layer privacy protections in ADR-0036.

These are not variations on one identifier. They describe three distinct things. This ADR
defines all three formally and resolves the derivation contradiction.

## Decisions

### Decision 1 — Enrollment ID

The **Enrollment ID** is a 128-bit opaque value assigned at first enrollment.

- **Generated by** the enrollment authority (not the chip manufacturer or the chip itself).
- **Independent of chip hardware**: it does not derive from the JCOP chip's hardware serial,
  certificate, or key pair. The chip holds its own hardware identity for PKI purposes; the
  Enrollment ID is a separate namespace.
- **Deterministically reissuable**: generated from `HKDF(account_secret, enrollment_sequence)`
  — where `account_secret` is a secret held by the enrollment authority and
  `enrollment_sequence` is a monotonic counter per person. If the account is not revoked,
  the same Enrollment ID can be regenerated for a replacement tag. This resolves the
  ADR-0049 contradiction: physical elements remain valid after a card swap because the
  Enrollment ID is account-bound, not chip-bound.
- **Never exposed raw** to unauthenticated readers. It is provisioned onto the JCOP applet
  at enrollment and returned only to authenticated, authorised sessions.

This refines ADR-0057 Decision 2, which established that the UUID is enrollment-authority
assigned and not derived from chip hardware. That decision stands; this ADR specifies the
generation mechanism.

### Decision 2 — Pairwise RP ID

The **Pairwise RP ID** is a per-tenant derived identifier, unchanged from ADR-0024.

`pairwise_rp_id = HMAC-SHA256(enrollment_id, tenant_id)[0:16]`

- Presented post-authentication to relying parties.
- Non-correlatable across tenants: a healthcare RP and a military RP see different values
  for the same person.
- Not the Enrollment ID; not the Session Token.
- Unchanged from ADR-0024's intent; this ADR adds the derivation formula.

### Decision 3 — Session Token

The **Session Token** is a 128-bit random value generated fresh on each NFC power cycle.

- Presented pre-authentication to any reader (per ADR-0057 Decision 1).
- Provides no linkage to the Enrollment ID.
- Enables a reader to initiate an authenticated session without disclosing identity.
- Changed every time the tag enters and exits the NFC field.

### Decision 4 — Tag Locator and engraved short-ID

The **Tag Locator** (the value physically engraved on the tear-away and grommet) is a
short, stable, human-readable derivative of the Enrollment ID:

`locator = Base32(HMAC-SHA256(enrollment_id, "hexa.locator.v1")[0:5])`  (8 chars)

Properties:
- **Stable across card replacements**: same Enrollment ID → same locator on new tag.
- **Independent of the digital identifier space**: not derivable from the Session Token
  or the Pairwise RP ID.
- **Not derivable from chip hardware**: consistent with Decision 1.
- **Publicly visible**: physically engraved; anyone who handles the tag can read it.

**Explicit acceptance of OQ-23's privacy trade-off:**

OQ-23 noted that a stable physical engraving is a tracking vector at the physical layer,
bypassing the software-layer unlinkability work in ADR-0024/ADR-0036. This trade-off is
accepted here. Physical identification inherently requires a stable visible identifier.
The Tag Locator is not a secret; it is the physical fallback identification mechanism.
The privacy protections in ADR-0024/ADR-0036 operate at the digital/NFC layer and are not
undermined by the physical engraving — they serve different threat models:
- **NFC layer**: protects against passive RF surveillance and reader tracking.
- **Physical layer**: deliberately stable, for identification of an incapacitated person.

The Locator is not the full Enrollment ID and cannot be used to derive it. It is a
one-way 40-bit truncation — sufficient for physical identification, insufficient for
digital correlation without knowledge of the Enrollment ID.

**Amendment to ADR-0040:**
ADR-0040's short-ID derivation from the chip UUID is superseded by this Decision.
The engraved short-ID is the Tag Locator as defined here.

## Principle tests

**P2 (tag is cache, not identity):**
Enrollment ID is account-bound, not chip-bound. A destroyed tag is replaced with a new JCOP
provisioned with the same Enrollment ID. Physical elements (tear-away, grommet engraving)
remain valid because the Tag Locator derives from the Enrollment ID, not the chip. Full
restoration on a new tag requires no data from the old tag. ✓

**P5 (owner controls content, down to zero):**
Identifiers are infrastructure, not content. The owner controls what data is stored under
their Enrollment ID. The Pairwise RP ID and Session Token expose no data the owner has not
consented to disclose. The Tag Locator on the physical element is committed at enrollment;
the owner understands this is a stable physical identifier. ✓

**P7 (no personal data on immutable ledgers):**
No identifier defined here is written to an immutable ledger. The Enrollment ID is in the
backend account record (mutable). The Tag Locator is on the physical element (not a ledger).
The transparency log records read receipts, not identifiers. ✓

**P9 (identity/signing require user verification; medical read never does):**
Identifiers do not by themselves trigger signing or identity operations. Session Token is
returned pre-auth (no personal data). Enrollment ID is returned only to authenticated
authorised sessions. ✓

## Consequences

**What becomes possible:**
- A single authoritative definition resolves the ADR-0040 / ADR-0049 / ADR-0057 contradiction.
- Replacement tags are straightforward: same Enrollment ID, same Tag Locator, same physical
  elements.
- OQ-23 is resolved with an explicit, reasoned acceptance of the physical tracking trade-off.

**What becomes harder:**
- The enrollment authority must implement deterministic Enrollment ID generation and hold
  the account_secret securely. Loss of account_secret makes Enrollment ID regeneration
  impossible (a new one would be assigned, invalidating physical elements).
- The locator derivation must be reproduced identically for every reissue.

**What we give up:**
- The option of deriving the short-ID from chip hardware (ADR-0040's original approach).
  That approach made the physical engraving a function of the chip and was incompatible
  with ADR-0049's reissue model.
